## 구현 결과

### GameDB 리팩토링

기존에는 GameDB에서 하는 기능이 적었습니다. (로그인 체크, 유저 등록, 로그아웃, 데이터 로드)

하지만 이후 추가할 출석체크 기능이나 재화 로드 등 DB에 상호작용할 기능이 많아질 수록 GameDB에만 로직을 구현하기에는 코드 가독성이 점점 떨어졌습니다.

그래서 DB에 상호작용하는 기능을 여러 클래스로 분할하여 각자의 역할만 수행하도록 분할했습니다.

### 문제점

DB의 기능별로 클래스를 분리하여 작업을 진행하다보니 클라이언트와의 마지막 통신 시간을 기록하는데에 어려움이 있었습니다. 

클래스를 분리하게 되면, 통신 시간을 기록하는 함수를 매 클래스마다 만들어야 해서 중복 코드가 늘어나는 문제가 있는 것이었습니다.

### 개선 방향 - partial class 사용

그래서 DB의 기능별로 클래스를 분리하는 것이 아닌, partial class를 활용하여 하나의 클래스만 사용하되, 파일만 분리하여 구현하는 방식으로 변경했습니다.

---

### Service 클래스 추가

기존 서버의 구조는 Controller - DB의 구조로, 어떤 기능에 대한 검증 로직을 수행할 때 Controller와 DB 클래스에서 분산하여 작성했었습니다.

하지만 로직을 추가하면서, Controller와 DB의 클래스가 하는 역할이 점점 늘어나는 현상이 생겼습니다. 그로 인해서 코드의 길이도 늘어나 가독성이 좋지 않게 됐습니다.

그래서 Controller와 DB 클래스 사이에 Service라는 비즈니스 클래스를 추가하여 기존에 Controller와 DB클래스에서 진행하던 검증 로직을 전부 Service 클래스에 구현하였고 Controller는 데이터의 수신과 송신만을, DB는 데이터베이스로부터 필요한 데이터를 반환하거나 업데이트만을 하도록 변경하였습니다.

---

### DB 트랜젝션 함수 추가

데이터베이스를 통해 유저 정보를 업데이트하는 과정에서 동시에 하나가 아닌 여러 테이블을 업데이트해야 하는 상황이 있었습니다.

여러 테이블을 업데이트 하는 과정에서 중간에 오류가 나게되면 이전에 진행하던 작업을 롤백해야 하는데, 기존에는 작업을 롤백하는 기능이 없었습니다.

그래서 트랜젝션 함수를 추가하여 여러 테이블의 업데이트를 수행하게 되면 트랜젝션을 수행하도록 함수를 추가했습니다. 

---

### 출석 체크 기능 추가

출석체크 시스템을 구현했습니다.

데이터베이스에는 유저의 마지막 출석시간, 그리고 출석횟수를 저장하였고, 출석 시도시 출석 시간을 비교하여 출석이 가능하면 출석정보를 업데이트 후 결과를 반환하는 방식을 사용했습니다.

---

### 업그레이드 기능 추가

유저의 스탯을 강화하는 업그레이드 기능을 구현했습니다.

초기에는 업그레이드 정보를 유저의 스탯 정보에 같이 넣으려 했으나, 업그레이드의 수가 늘어날 수록 관리하기가 힘들어질 것 같았습니다.

그래서 별도의 유저 업그레이드 테이블을 제작하여 {유저id, 업그레이드id, 업그레이드 레벨} 정보를 저장하는 방식으로 테이블을 구성했습니다.
